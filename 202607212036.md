# Commvault MySQL Backup

Commvault supports two backup operations for [MySQL](202607191021.md):
**full** and **incremental**. These backup will protect the [Binary
Logs](202607191049.md), includes commit or uncommit transactions.

We could back up MySQL using Commvault interface (Command Center or CommCell
Console) or MySQL Enterprise Backup with SBT.

For command line backup, see more in [Commvault MySQL Command Line
Backup](202607251938.md)

Commvault support block-level backup for MySQL but only on
[Linux](202204081225.md) machine.

When there are multiple transaction logs backups run in parallel on more than 2
subclient, each log file backed up only once. **Only one log backup job** run at
a time. If multiple backup jobs are initiated at the same time, they are run
sequentially in a queue.

The command `mysqldump --master-data --snigle-transaction` used for back up.
See more in [mysqldump](202607212057.md). `flush table` is executed
implicitly by the command to ensure database [consistency](202607182204.md).

During backup of the default subclient, the [Commvault MySQL
iDA](202607191025.md) will automatically discovery new databases, then add them
to the default subclient.

Commvault will back up [MySQL System Database](202607191044.md), user
database, and [Binary Log](202607191049.md). It would not back up MySQL
application files, OS data, MySQL server database named `information_schema`,
MySQL server database named `performance_schema`. To back up these data, we
have to utilise file system backup.

Full backup must be performed before transaction log can be initiated or
applied. It can be restored to the time of the backup, but not to a
point-in-time between backups.

Incremental backup is consistent with the start time of the backup, making
point-in-time recovery possible. Each time transaction log is backed up, they
are truncated to the exact time of the backup. Since there is no checkpoint
issued at this time, the dirty pages are not written to the disk before or after
the incremental. If there are dirty pages, any completed transaction must be
rolled forward if a transaction log restore performed. If any transaction is not
completed at the time of incremental backup is performed, it is rolled back
during the restore involving the incremental backup.

**Note**: Dirty pages are the pages that are changed but not yet added to the
data files.
